Uncertainty and confidence in depth estimation

Listen to this page

Why a depth model should not be trusted equally everywhere

A depth network always outputs a number, even for a black glass door at night. Nothing in a plain depth map tells you which pixels are solid estimates and which are guesses. Uncertainty estimation adds a second map that says how much each value can be trusted.

What uncertainty means in a depth prediction

Kendall and Gal separate two kinds [12]. Aleatoric uncertainty comes from the data itself: glass, darkness, motion blur and textureless walls are hard no matter how good the model is. Epistemic uncertainty comes from the model's limited experience: a staircase seen from an odd angle may simply be unlike anything in training. Aleatoric uncertainty can be predicted by the network directly, by adding an output channel and training it with a loss that lets the model admit doubt at a cost. Epistemic uncertainty needs several different "opinions" from the model.

Poggi and colleagues compared many of these for monocular depth [15]. They judged each method by how much the error drops when the most uncertain pixels are removed first, which is the right question for a safety system. Methods that combine several sources of uncertainty tended to rank errors best. For a pretrained model such as Depth Anything V2 that we do not want to retrain, test time augmentation is the most practical place to start:

import numpy as np

def depth_with_uncertainty(run_model, image):
    """Cheap uncertainty for a frozen model using test time augmentation.

    run_model(image) -> HxW metric depth. image is an HxWx3 numpy array.
    """
    preds = [run_model(image),
             np.fliplr(run_model(np.fliplr(image)))]          # mirrored copy
    for gamma in (0.8, 1.25):                                 # darker and brighter copy
        preds.append(run_model(np.clip((image / 255.0) ** gamma * 255, 0, 255)))
    preds = np.stack(preds)
    mean = preds.mean(axis=0)
    std = preds.std(axis=0)
    rel_unc = std / np.maximum(mean, 1e-3)    # 0.10 means "about plus or minus 10 percent"
    return mean, rel_unc

Using confidence thresholds before giving guidance

The relative uncertainty (spread divided by depth) is compared with a threshold. Below it, the system speaks a distance. Above it, the system says it is unsure and asks the user to slow down or pan the camera, which gives the model a fresh view:

def guidance(zone_depth, zone_unc, near=1.5, tau=0.20):
    """Decide what to say for the walking corridor.

    zone_depth : nearest depth in the center zone (m), e.g. 10th percentile
    zone_unc   : relative uncertainty at that point (std / mean)
    """
    if zone_unc > tau:
        return "Depth estimate uncertain. Move the camera slowly."
    if zone_depth < near:
        return f"Stop. Obstacle about {zone_depth:.1f} meters ahead."
    if zone_depth < 3.0:
        return f"Obstacle about {zone_depth:.0f} meters ahead."
    return None   # stay quiet: silence is better than chatter

The threshold should be chosen on recorded test data rather than guessed. Lowering it makes the system say "unsure" more often but gives fewer confidently wrong distances. For navigation I would favor a low threshold, as long as the "unsure" message does not appear so often that users stop listening.

How uncertainty improves safety

Uncertainty gives the system a third answer beyond "obstacle" and "clear." That third answer is, in my opinion, the single most important feature for an assistive device, because it is what prevents the confidently wrong guidance described in Part 1.
