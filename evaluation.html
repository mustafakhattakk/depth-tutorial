Evaluating depth models

Listen to this page

Comparing predictions with ground truth

Depth models are scored against sensor measured depth on benchmarks such as NYU Depth V2 [5] and KITTI [6]. Three numbers appear in nearly every paper:

  • AbsRel, the average absolute error divided by the true depth. An AbsRel of 0.06 means the typical pixel is off by about 6 percent. Lower is better.
  • RMSE, the root mean squared error in meters. It punishes large mistakes heavily. Lower is better.
  • δ1, the share of pixels whose prediction is within 25 percent of the truth. Higher is better.
import numpy as np

def depth_metrics(pred, gt, mask):
    p, g = pred[mask], gt[mask]
    abs_rel = np.mean(np.abs(p - g) / g)
    rmse = np.sqrt(np.mean((p - g) ** 2))
    ratio = np.maximum(p / g, g / p)
    delta1 = np.mean(ratio < 1.25)        # share of pixels within 25 percent
    return {"AbsRel": abs_rel, "RMSE": rmse, "delta1": delta1}

An important detail: relative models are scored after aligning each prediction with the ground truth using scale and shift, exactly as in Part 4. That alignment uses the true answer, so relative scores look better than what the model can achieve on its own. Always check which protocol a paper uses before comparing numbers.

The progress in ten years is striking: the typical error dropped from about one fifth of the true distance to about one twentieth. These are averages over many pixels, however. They say little about the worst cases, which are what matter for safety.

Testing on unseen scenes, indoors and outdoors

A fair test uses datasets the model never saw. MiDaS made this the standard for relative depth [3], and challenge benchmarks now test zero shot accuracy on hard scenes [16]. Indoor and outdoor results should be reported separately because their depth ranges differ by an order of magnitude.

Measuring processing speed

A model that takes one second per frame is not usable for walking guidance. FastDepth [20] showed that a carefully designed and pruned network can run in real time on an embedded board, at the cost of much lower accuracy than today's foundation models. Speed should be measured on the target phone, including image resizing, not just on a desktop GPU.

Testing whether uncertainty identifies bad predictions

Uncertainty is evaluated with sparsification curves [15]: remove the most uncertain pixels first and watch how fast the remaining error drops. If uncertainty is good, the error falls quickly. The area between this curve and the best possible one (AUSE) summarizes it in one number.

An evaluation designed for navigation

For an assistive app I would add four checks that standard benchmarks skip: distance error only in the 0.5 to 3 meter range, error only in the center walking corridor, the share of real obstacles within 1.5 meters that trigger a warning, and the "false clear" rate, meaning how often the system says the path is clear when it is not. That last number is the one I would most want to minimize.
