Converting relative depth into metric depth

Listen to this page

Why foundation models start with relative depth

The strongest depth models learn from huge, mixed collections of images, and only relative supervision lets those collections be combined. Metric ability is added afterwards. There are two practical routes: fine tune the model on metric data, or calibrate the relative output with a few known measurements at run time.

Route A: metric fine tuning

Here the pretrained encoder is kept and the model is trained further on data with real distances and known cameras. Depth Anything V2's metric models do exactly this [9]. ZoeDepth [10] adds a lightweight metric head that predicts depth as a mixture of adaptive "bins," plus a small router that picks an indoor or outdoor head for each image. Depth Pro [11] goes further and estimates the camera's focal length itself, so it does not rely on phone metadata. Using a fine tuned model takes only a few lines:

# pip install transformers torch pillow
from transformers import pipeline
from PIL import Image

# Depth Anything V2 fine tuned on indoor metric data (see the model card on Hugging Face)
depth = pipeline("depth-estimation",
                 model="depth-anything/Depth-Anything-V2-Metric-Indoor-Small-hf")

result = depth(Image.open("hallway.jpg"))
depth_m = result["predicted_depth"].squeeze().numpy()   # values in meters
print("closest point:", depth_m.min().round(2), "m")

Route B: calibrate with known distances

If a relative model is accurate up to scale and shift in inverse depth, two or more pixels with known distance are enough to recover the missing numbers. This is the algorithm I would use on a phone that has a few reliable distance readings, for example from AR plane detection, a single point time of flight sensor, or a known camera height above the floor.

  1. Run the relative model to get a disparity map.
  2. Collect pixels with known depth and convert those depths to inverse depth.
  3. Fit a straight line between predicted disparity and true inverse depth with least squares. Its slope is s and its intercept is t.
  4. Apply the line to every pixel and invert to get meters.
  5. Check the fit error. A large residual means the scene does not follow the model's assumptions, which is itself a warning sign.
import numpy as np

def align_scale_shift(pred_disp, known_depth, mask):
    """Turn relative disparity into metric depth using a few known distances.

    pred_disp   : HxW relative disparity from MiDaS or Depth Anything (bigger = closer)
    known_depth : HxW array of measured depths in meters (only valid where mask is True)
    mask        : HxW boolean array marking the pixels whose depth we know
    """
    x = pred_disp[mask].ravel()
    y = 1.0 / known_depth[mask].ravel()            # the model is affine in inverse depth
    A = np.stack([x, np.ones_like(x)], axis=1)      # columns: x and 1
    (s, t), *_ = np.linalg.lstsq(A, y, rcond=None) # least squares fit of y ≈ s*x + t
    disp_metric = np.clip(s * pred_disp + t, 1e-3, None)   # avoid dividing by zero
    return 1.0 / disp_metric, s, t                  # depth in meters, plus the fit

A worked example

Suppose the model outputs disparity 0.80 at a pixel we know is 1.0 meter away, and 0.20 at a pixel 4.0 meters away. The true inverse depths are 1.0 and 0.25. Solving 0.80s + t = 1.0 and 0.20s + t = 0.25 gives s = 1.25 and t = 0. A third pixel with predicted disparity 0.50 then maps to inverse depth 0.625, which is 1.6 meters. With more than two anchors, least squares averages out their noise.

Comparing the two routes

ApproachStrengthsWeaknessesUse when
Metric fine tuned model (Depth Anything V2 Metric, ZoeDepth)No extra sensor, one forward passCan be biased on new cameras and scene typesPlain phone camera, scenes similar to training
Metric model with focal estimation (Depth Pro, Metric3D)Handles different camerasHeavier models, slower on phonesUnknown or varied cameras, offline use
Relative model plus calibrationUses strong zero shot models, scale is anchored to realityNeeds reliable anchors in every frame or a stable scalePhone with AR tracking or a small range sensor

My recommendation for an assistive app is to combine them: run a metric model, but whenever reliable anchors are available, compare against them. If the two disagree by more than about 20 percent, treat the frame as uncertain. This turns calibration into a free reliability check.
